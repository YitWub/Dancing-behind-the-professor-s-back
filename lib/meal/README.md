# C필러 — 학식 / 창보 vs 학식 대결

> 답하는 질문: **"오늘 어디서 먹지?"**
> 그리고 이 필러가 진짜로 증명하려는 것: **"데이터가 모자랄 때 입을 다무는 법"**

## 1. 크롤링 대상과 실패 정책

### 1-1. 조사 결과 (2026-09-23 기준)

| 후보 | 결과 |
|---|---|
| `life.hanyang.ac.kr` (HY-SQUARE, ERICA 생활포털) | 식단 담당 포털이 맞음. **그러나 Phase 1 디자인 시스템 단계** |
| └ `life.hanyang.ac.kr/api/cafeteria/menus` | **HTTP 404** — 아직 구현 안 됨 |
| └ `theme/assets/js/mock-data.js` | 식단이 서버가 아니라 **클라이언트 목 데이터**에 박혀 있음. 파일 주석에 `MOCK — DB 연동 시 /api/cafeteria/menus 응답으로 교체` 라고 적혀 있음 |
| `fnb.hanyang.ac.kr/front/fnbmMdMenu` | 서울 캠퍼스(에비뉴) 전용. ERICA 식단 없음 (문서 내 'ERICA' 언급 0회) |

**결론: 현재 공개된, 파싱 가능한 ERICA 식단 엔드포인트가 존재하지 않는다.**

목 데이터를 긁어다 "오늘의 학식"이라고 보여줄 수도 있었지만 하지 않았다.
출처가 목 데이터인 걸 알면서 진짜인 척 보여주는 건 이 앱이 하지 말자고 한 바로 그 짓이다.

### 1-2. 그래서 크롤러는 이렇게 동작한다

`scripts/crawl-meals.ts` 는 **어떤 경우에도 예외로 죽지 않고, 반드시 `data/meals.json` 을 남긴다.**

```
① life.hanyang.ac.kr/api/cafeteria/menus  (JSON 파서)
     ↓ 실패
② life.hanyang.ac.kr/.../facilities/index.php  (HTML 표 파서)
     ↓ 실패
③ 직전 성공분 캐시            → ok:false, fallback:'cache'
     ↓ 없으면
④ data/meals.seed.json       → ok:false, fallback:'seed'
```

| 상태 | `ok` | `fallback` | 화면 |
|---|---|---|---|
| 크롤링 성공 | `true` | 없음 | 그냥 식단 표시 |
| 실패 + 캐시 있음 | `false` | `'cache'` | "최신 식단을 못 가져왔습니다(마지막 수집분 표시 중)" |
| 실패 + 시드 | `false` | `'seed'` | **"식단을 못 가져왔습니다(시드 데이터 표시 중)"** |

지금 실행하면 항상 ④ 로 떨어진다. 그게 사실이므로 그렇게 표시한다.

> 파서 자체는 죽어 있지 않다. JSON·HTML 양쪽 파서를 실제 응답 형태
> (HY-SQUARE mock-data.js 가 선언한 스키마)에 맞춰 구현하고 픽스처로 검증해 두었다.
> 엔드포인트가 열리는 날 코드 수정 없이 ① 경로를 탄다.

외부 HTTP 라이브러리는 쓰지 않았다 (`cheerio` 등 추가 의존성 없음).
`fetch` + 정규식 파서로만 구성 — CONTRACT.md 3장 "외부 런타임 의존성 추가 금지" 준수.

### 1-3. 크롤링 예절

- User-Agent 에 봇임을 명시 (`erica-life-meal-bot/0.1`)
- 요청 1회당 엔드포인트 2개, 12초 타임아웃
- 로그인/인증이 필요한 페이지는 건드리지 않음

## 2. 창보 vs 학식 — 승부 판정 임계치

### 2-1. 왜 임계치가 필요한가

후기 2건으로 "창보 승"이라고 쓰는 순간, 이 앱의 다른 모든 숫자도 못 믿게 된다.
A필러(학점)가 "이 예측은 사실상 동전던지기"를 고백하기로 한 것과 같은 규칙이다.

### 2-2. 판정 조건 — 셋을 **모두** 통과해야 `decisive: true`

| # | 조건 | 값 | 근거 |
|---|---|---|---|
| ① | 진영당 최소 후기 수 | `MIN_REVIEWS_PER_SIDE = 5` | 5건 미만이면 한 사람의 극단 평가가 평균을 0.4점 이상 흔든다. 5건이면 1건당 영향이 0.2점 이하로 떨어져 ②의 최소폭 아래로 들어간다 |
| ② | 평점 차이 최소폭 | `MIN_RATING_GAP = 0.4` | 1~5 척도에서 0.4는 5건 기준 "한 명이 별 2개 차이로 다르게 준 정도". 이보다 작은 차이는 메뉴 차이가 아니라 표본 차이로 보는 게 맞다 |
| ③ | 차이가 표본오차 밖 | 95% 신뢰구간 (`z = 1.96`, Welch 근사) | 후기 수가 적고 분산이 크면 평균 차이가 커도 우연일 수 있다. `gap ≥ 1.96 × √(s₁²/n₁ + s₂²/n₂)` |

보조 장치 하나 더: **표본표준편차 하한 `STDEV_FLOOR = 0.5`**.
후기 3건이 우연히 전부 별 5개면 분산이 0이 되어 "오차 0, 확실한 승리"가 나온다.
그건 통계가 아니라 사고라서, 표준편차를 최소 0.5로 깔고 계산한다.

### 2-3. 실제로 이렇게 갈린다 (시드 데이터 기준)

| 상황 | n (창보/학식) | 평점 | 판정 |
|---|---|---|---|
| 09-23 중식 | 11 / 13 | 4.3 vs 3.5 | ✅ `decisive: true`, winner: `changbo` — *"오늘 중식은 창업보육센터 판정승"* |
| 09-23 석식 | 3 / 2 | 4.0 vs 3.0 | ❌ `decisive: false`, winner: `null` — *"오늘 석식은 무승부 — 표본이 너무 적습니다 (창업보육센터 3건 / 학생식당 2건)"* |
| 09-22 중식 | 8 / 9 | 3.9 vs 4.0 | ❌ `decisive: false` — *"오늘 중식은 무승부 — 평점 차이가 오차 범위 안입니다"* |

석식은 평점 차이가 **1.0점이나 나는데도** 승부를 유보한다. 이게 핵심이다.
차이가 커 보인다고 표본 5건 미만에서 승자를 선언하지 않는다.

### 2-4. 추세 (`trend`)

같은 끼니 기준 최근 7일을 **최근 3일 vs 그 이전 4일**로 갈라 평균을 비교한다.

- 양쪽 구간 모두 후기 3건 이상일 때만 판정 (`TREND_MIN_N = 3`)
- 차이 `±0.25` 이상이면 `up` / `down`, 아니면 `flat`
- **표본이 모자라면 무조건 `flat`** — "모르면 흐리게"

### 2-5. 연승 (`headline`)

같은 끼니 기준으로 하루씩 거슬러 올라가며 같은 진영이 계속 이겼는지 센다 (최대 10일).
**판정이 유보된 날은 연승을 끊는다** — "무승부였지만 사실상 우리가 이겼다"는 계산을 하지 않는다.

- 3연승 이상 → `"오늘 중식도 창보 판정승 — 학식 3연패"`
- 2연승 → `"오늘 중식은 창보 2연승"`
- 그 외 → `"오늘 중식은 창업보육센터 판정승"`

## 3. 파일 구성

| 파일 | 역할 | 클라이언트에서 import 가능? |
|---|---|---|
| `battle.ts` | 대결 판정 로직 + 라벨 + 임계치 상수 | ✅ **순수 모듈** (`node:fs` 없음) |
| `store.ts` | `data/*.json` 읽기/쓰기 + `getBattle()` 서버 래퍼 | ❌ 서버 전용 (`node:fs`) |
| `review.ts` | `MealReview` CRUD + 입력 검증 | ❌ 서버 전용 (store.ts 경유) |

**팀원3 주의**: `CAFETERIA_LABELS`, `computeBattle()`, `MIN_REVIEWS_PER_SIDE` 같은 건
반드시 `battle.ts` 에서 가져오세요. `store.ts` 를 클라이언트 컴포넌트에서 import 하면
`node:fs` 가 번들에 딸려 들어와 빌드가 깨집니다.
(원래 `getBattle()` 이 battle.ts 에 있어서 battle.ts 전체가 오염돼 있었는데, 분리했습니다.
CONTRACT.md 3장 "계산은 전부 클라이언트에서 가능한 순수 함수" 를 지키기 위한 조치입니다.)

`data/meal-reviews.json` 이 없으면 `meal-reviews.seed.json` 에서 출발하고,
`POST /api/meals/review` 가 처음 들어오는 순간 생성된다.

### ⚠️ "오늘"은 반드시 KST 기준으로

`new Date().toISOString().slice(0, 10)` 는 **UTC 날짜**다. KST 는 UTC+9 이므로
**00:00~09:00 사이에는 어제 날짜가 나온다.** 아침 먹으러 가는 시간대가 정확히 이 구간이라,
오전 8시에 앱을 열면 어제 식단이 뜬다.

날짜 기본값·기준일 계산은 전부 **`lib/datetime.ts`** 의 `kstToday()` / `kstYear()` 를 쓴다.
(원래 `lib/meal/kst.ts` 였으나 A필러·화면도 같은 함정을 밟으므로 공유 계약으로 승격됐다.
CONTRACT.md 9장: **"오늘"이 필요하면 반드시 거기를 쓸 것. `new Date().toISOString()` 직접 호출 금지.**)
(`addDays()` 내부의 `toISOString()` 은 이미 `YYYY-MM-DD` 로 정규화된 값을 UTC 자정으로
다루는 것이라 그대로 두는 게 맞다 — 여기는 시간대 개념이 없다.)

### ⚠️ 시드 식단은 기준일 앞뒤 2주만 덮는다

기본 기준일은 `2026-09-23`, 범위는 `2026-09-14 ~ 2026-09-27` 이다.
**오늘 날짜가 이 범위를 벗어나면 `/api/meals?date=<오늘>` 이 빈 배열을 돌려주고,
대결도 전부 "아직 후기가 없습니다" 가 된다.** 발표일이 범위 밖이면 기준일을 옮겨 다시 구울 것:

```bash
node scripts/make-seeds.ts --anchor=2026-11-05
node scripts/make-seeds.ts --anchor=today
npm run crawl && npm run score        # 산출물도 같이 갱신
```

기준일을 옮겨도 **대결 3종 시나리오(판정승 / 표본부족 유보 / 무승부)는 기준일 상대로
정의돼 있어 그대로 따라온다.** PRNG 시드가 고정이라 같은 기준일이면 언제 돌려도 같은 결과다.
`npm run seed` 는 오늘이 범위 밖이면 경고를 찍는다.

## 4. 화면(팀원3)이 반드시 표시해야 할 것

1. `GET /api/meals` 응답 헤더 `X-Meal-Ok: false` 면 → **"식단을 못 가져왔습니다(시드 데이터 표시 중)"** 배지
   (상세가 필요하면 `GET /api/meals/status` 가 `CrawlResult` 전문을 준다)
2. `BattleResult.decisive === false` 면 → **승자 표시 금지**. `headline` 문구를 그대로 쓸 것
3. `BattleStanding.avgRating === null` (후기 0건) → 숫자 대신 "후기 없음"
4. `trend: 'flat'` 은 "변화 없음"이 아니라 "**판단할 만큼 후기가 없음**"일 수 있다 — 화살표를 회색으로
5. **`X-Meal-Fetched-At` 이 오래됐으면 수집 시각을 같이 띄울 것.**
   `X-Meal-Ok: true` 는 "언젠가 크롤링에 성공했다"이지 "지금 식단이 최신이다"가 아니다.
   크롤러를 며칠 안 돌리면 오래된 식단이 **성공 상태 그대로** 뜬다 — 화면상 아무 이상이 없다.
   하루 이상 지났으면 "N일 전 수집" 을 붙여서, 침묵이 최신처럼 보이지 않게 할 것.
   (`fetchedAt` 은 `CrawlResult` 에도 들어 있고 `/api/meals/status` 로도 받을 수 있다.)
