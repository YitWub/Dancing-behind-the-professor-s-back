# BOKAK 학점 관리 — 제품 철학과 UX 설계 기준

> **학점 기능을 수정하기 전에 이 문서와 루트의 [AGENTS.md](../../AGENTS.md),
> [CONTRACT.md](../../CONTRACT.md)를 먼저 읽는다.** 다른 작업 세션에서도 동일하게 적용한다.
> 이 문서는 앞으로의 설계·리뷰 기준이다. 현재 구현이 모든 기준을 충족한다는 뜻은 아니다.
> 파일 소유권, 공통 규칙, 계산 엔진의 변경 승인 범위를 확대하지 않는다.

**입력은 적게, 결과는 풍부하게, 사용은 재미있게.**

## 1. 누구를 위한 서비스인가

핵심 사용자는 이미 Notion 등으로 자기 관리를 잘하는 학생이 아니다.
**관리하고 싶지만 기록하고 설정하는 과정이 귀찮아서 실천하지 못하는 대학생**이다.
기능의 수보다 적은 노력으로 다음 행동을 결정할 수 있는지가 중요하다.

- 사용자 입력은 결과에 꼭 필요한 최소한으로 제한한다.
- 과목 반영비율 등 이미 저장된 정보는 재사용하고 다시 묻지 않는다.
- 계산 가능한 값은 앱이 계산한다. 알 수 없는 사실을 자동으로 만들어내지는 않는다.
- 복잡한 내부 시스템을 유지하기 위해 사용자에게 추가 설정을 떠넘기지 않는다.
- 매번 기록하도록 요구하기보다 예외가 생겼을 때만 기록할 수 있게 한다.
- 결과를 확인하고 행동을 고르는 가치가 데이터 입력의 부담보다 커야 한다.
- 새 기능은 기본 화면에 항목을 더하기 전에 기존 흐름에 통합할 방법부터 검토한다.

## 2. 요약 탭은 하나의 사용자 흐름이다

| 순서 | 사용자의 질문 | 먼저 보여줄 결과 | 다음 행동 |
|---|---|---|---|
| ① 현재 상태 | 지금 어디까지 왔지? | 확보·미확보·상실, 현재 최고 가능 총점 | 현재 흐름 확인 |
| ② 현재 예상 성적 | 지금처럼 하면 어떻게 될까? | 예상 등급 또는 계산 가능한 전망, 추정 상태 | 원하면 근거 펼치기 |
| ③ 목표 선택 | 나는 어떤 학점을 원하지? | A+·A0·B+ 등의 간단한 선택 | 목표 분석 자동 실행 |
| ④ 앞으로 할 일 | 그래서 지금 뭘 해야 하지? | 시험·과제·출석의 행동 카드 | 기록 또는 해당 평가 관리 |

기능을 독립된 패널로 나열하지 않는다. 예상 결과는 목표 선택으로,
목표 선택은 구체적인 행동으로 이어져야 한다. 같은 비교 결과를 여러 카드에서 반복하지 않는다.

### 실제 성적 막대

- 표시 영역은 **확보 / 아직 확보하지 않은 배점 / 상실** 세 가지를 유지한다.
- 초록색 확보 영역, 빈 배점, 오른쪽에서 깎인 상실 영역의 의미를 일관되게 유지한다.
- 내부 계산에서는 채점 대기와 예정 배점을 구분한다. 표시만 미확보로 합친다.
- 확보·미확보·상실은 평가비율 합계가 100%이고 분류 가능한 경우 100점이 된다.
- 배점 불명확·기존 기록 검토가 필요하면 검증 완료나 정확한 합계처럼 표현하지 않는다.
- 최고 가능 총점은 확정 상실과 별도 최종 감점의 적용 여부를 밝혀 표시한다.
- 가상 시험 점수나 출석 추정 감점을 실제 확보·상실에 합산하지 않는다.

## 3. 현재 예상 학점: 결과를 먼저, 이유는 짧고 구조적으로

기본 화면은 **등급 + 예측 상태 한 줄 + 근거를 여는 행동**으로 구성한다.
예: `예상 A0 · 가정 기반`. 결과와 상태를 함께 읽을 수 있어야 한다.
정보 부족이나 등급 경계의 불확실성은 접힌 설명 속에만 숨기지 않는다.
3초 안에 핵심 결과와 그 결과가 확정인지 추정인지 파악할 수 있어야 한다.

‘왜 이 학점인가요?’를 펼치면 핵심 근거 2~3개부터 보여준다.
아래의 분류를 짧은 행·배지·카드로 표현하고 긴 문단으로 나열하지 않는다.

| 종류 | 예시 | 의미 |
|---|---|---|
| 확정 | 중간고사 54.5 / 100점 | 사용자가 입력한 실제 결과 |
| 가정 | 기말고사 54.5 / 100점 | 현재 흐름을 이어간다는 시나리오 |
| 가정 | 남은 과제 평균 100점 | 완료분 또는 명시한 조건을 적용한 예상 |
| 미확인 | 기말 실제 평균·다른 학생의 최종 성적 | 아직 알 수 없는 사실 |

예시는 UI 구조 설명이며 모든 과목에 이 숫자를 기본 적용하라는 뜻이 아니다.
복잡한 수학식·분포 이름은 추가로 필요한 사용자만 확인하도록 분리한다.
결과 영역에 시험 점수별 비교 카드를 다시 나열하지 않는다. 행동 비교는 목표 플래너가 담당한다.

## 4. 목표 학점 플래너: 입력 계산기보다 행동 안내

사용자 입력은 **“나는 A0를 받고 싶어요.”**가 중심이다.
이미 있는 기록과 평가비율로 분석하며 여러 시험 점수부터 입력하라고 요구하지 않는다.

기본 화면의 우선순위:

1. 목표 등급 버튼과 현재 선택 상태.
2. 목표 가능 여부 또는 조건부 전망, 계산 가능한 핵심 점수.
3. 시험·과제·출석별 지금 해야 할 일.
4. 기본적으로 접힌 ‘계산 근거 보기’와 ‘예측에 사용한 가정’.

| 카드 | 보여줄 내용 | 주의할 점 |
|---|---|---|
| 시험 | 기말 추천 목표와 만점·점수 단위 | 원점수인지 최종 환산점수인지 구분 |
| 과제 | 남은 과제의 필요한 득점률 또는 추천 행동 | 다른 학생의 과제 점수를 모르면 상대 순위 상승을 수치화하지 않음 |
| 출석 | 추가 결석의 예상 감점이나 위험 | 점수 감점과 시험 응시 제한·F 판정을 구분 |

가능하면 균형·과제 우선·시험 우선 전략을 자동 제공한다.
배점상 시험 부담을 줄이는 전략을 공부 시간당 효율이 검증된 전략처럼 말하지 않는다.
정확한 등급 기준이 없으면 명시적인 조건부 시나리오 또는 목표 총점 분석을 제공할 수 있다.
목표 총점 입력을 기본 필수 과정으로 되돌리지 않고, 원점수 목표를 실제 상대등급과 동치로 두지 않는다.
계산되지 않는 값은 임의로 채우지 말고 필요한 정보나 가능한 분석만 보여준다.

## 5. 예측의 신뢰성과 불확실성

**우리는 예측기를 만들며 실제 최종 학점을 확정하지 않는다.**

- 확정 점수, 예상 점수, 추천 목표, 실제 등급 기준을 데이터와 표현에서 분리한다.
- 예정·채점 대기를 0점으로 처리하지 않는다. 확정 0점과 미제출 0점의 의미도 보존한다.
- 미래 시험·과제에 가정한 값을 실제 기록으로 저장하거나 HP바에 반영하지 않는다.
- 상대평가 A/B 배분 상한은 개인의 등급 획득 확률이 아니다.
- 상대평가 유형만으로 A+·A0 확률을 만들지 않는다. +/0 반반 등은 공식 규칙이 아닌 가정이다.
- 평균만으로 실제 분포·등수는 식별되지 않는다. 분포 가정에 따른 시나리오를 실측 통계나 검증된 확률로 표현하지 않는다.
- 과제의 내 점수만으로 다른 학생 대비 위치를 안다고 간주하지 않는다.
- 절대평가도 교수자의 실제 원점수 기준·환산 방식을 확인한다. 공통 최종점수표를 모든 원점수 합계에 무조건 대입하지 않는다.
- 정보 부족 시 가능한 총점 범위와 조건부 목표 분석을 우선한다. 넓은 범위만 제시하고 행동 안내를 끝내지는 않는다.
- 근거 없는 소수점 정밀도를 피한다. 유효한 확률을 제공할 때는 CONTRACT의 누적 표현·5~10% 단위 또는 단계형 표현을 따른다.
- 경계에 가까우면 작은 변화로 전망이 달라질 수 있음을 짧게 표시한다.
- 모델의 입력·가정·버전·적용 가능한 범위는 코드 및 기술 문서에서 추적 가능해야 한다.

### ‘기말 28점’ 같은 결과의 표현

금지: **“A0를 받으려면 기말 28점 이상이면 됩니다.”**

권장: **“기말 참고 목표 약 28 / 100점 · 조건부 추정”**.
기본 화면에서 실제 커트라인·달성 보장이 아님을 짧게 알린다.
상세에서는 원점수/환산점수, 만점, 사용한 반 평균과 출처, 목표 경계 설정,
과제·출석 포함 여부, 다른 미완료 평가의 처리 방식을 확인할 수 있어야 한다.
근거가 부족하면 숫자를 고집하지 않고 조건별 범위·정보 확인 상태로 전환한다.

### 기존 프로젝트 규칙과의 관계

[CONTRACT.md 2장](../../CONTRACT.md)의 정직성 규칙을 완화하는 문서가 아니다.
현재 평균만 사용하는 간이 모델은 분포 가정이 포함된 시나리오이며,
기존 통계 엔진의 정보 부족 시 등급 보류 원칙과 구분해야 한다.
표시 문구만 바꿔 가정을 데이터로 인정받거나 모델 검증을 대체할 수 없다.
가정을 명시하기 어렵거나 결과의 한계를 전달할 수 없으면 세부 등급을 보류한다.
확률 엔진의 수학 모델·공통 규칙 변경은 해당 담당자 협의 대상으로 유지한다.

## 6. 모바일 가독성과 상호작용

- 모바일 우선으로 설계하고 320~390px에서도 가로 넘침 없이 읽고 조작할 수 있게 한다.
- 중요한 숫자는 크게, 단위와 조건은 가까이에 배치한다.
- 한 카드에는 하나의 핵심 메시지만 둔다. 카드마다 간격·정렬·폰트 위계를 일관되게 한다.
- 목표 버튼 등 터치 영역은 충분히 확보하고 선택 상태를 명확히 표시한다.
- 색상만으로 상태를 구분하지 않는다. 짧은 상태 문구와 아이콘을 함께 사용한다.
- 접이식 영역은 키보드·터치로 열 수 있고 기본적으로 접혀 있어야 한다.
- 펼친 상세도 짧은 목록·행·표로 구성한다. 긴 회색 문단 블록으로 몰아넣지 않는다.
- 중요 정보가 없는 큰 카드·빈 공간·장식·중복 안내를 줄인다.
- 저장 실패 시 편집 내용을 유지하고 기존 데이터를 보존한다.

**정보를 많이 계산하는 것과 화면에 정보를 많이 표시하는 것은 다르다.**
내부 분석이 정교해져도 기본 화면에서 사용자가 읽어야 할 양은 늘리지 않는 것을 목표로 한다.

## 7. RPG 콘셉트는 표현의 확장이다

| 제품 개념 | 향후 RPG 표현 |
|---|---|
| 학점 목표 | 달성하고 싶은 목표 |
| 남은 시험·과제 | 앞으로 수행할 미션 |
| 출석 위험 | 주의해야 할 위험 요소 |
| 실제 성적 현황 | 진행도와 상태 |
| 목표 달성 전략 | 다음 행동 |

현재는 가독성 좋은 프로토타입이 우선이다. 캐릭터·경험치·레벨 시스템을 지금 추가하지 않는다.
테마를 바꿔도 점수·불확실성의 의미와 접근성은 유지한다.
미션 완료 버튼, 회차별 출석 체크 등 기록 부담을 늘리는 게임 요소를 추가하지 않는다.

## 8. 피해야 할 안티패턴

| 안티패턴 | 대신 할 일 |
|---|---|
| 기능을 추가할 때마다 설정·입력칸 추가 | 저장값 재사용과 자동 계산부터 검토 |
| 화면마다 같은 반영비율 재입력 | 과목 평가항목을 단일 출처로 사용 |
| 결과보다 모델 설명을 먼저 제시 | 핵심 숫자·상태 → 행동 → 접힌 근거 |
| 추정을 확정 등급·최소 보장 점수로 표현 | 조건부 전망과 미확인 정보를 함께 표시 |
| 목표 달성을 위해 여러 가상 점수부터 요구 | 등급 선택에서 전략 자동 분석 |
| 가정을 숨겨 입력 없는 정확도를 약속 | 필요한 가정만 명시하고 계산 한계를 구분 |
| 과제·출석을 시험 기반 상대 순위에 몰래 반영 | 총점 계산과 상대 위치의 적용 범위 분리 |
| 예측 값을 실제 점수로 저장 | 읽기 전용 시나리오와 실제 기록 분리 |
| 간편화를 위해 이전 데이터 삭제 | 원본 보존·필요한 전환 확인·저장 실패 복구 |
| 예쁜 색상·게임 요소 때문에 조작이 늘어남 | 읽기·행동·접근성을 먼저 검증 |

## 9. 다음 개편의 우선순위와 리뷰 질문

우선 적용할 것은 **예상 학점 상세 근거의 ‘확정 / 가정 / 미확인’ 구분**이다.
현재 정보 구조를 유지하면서 긴 기술 설명을 짧은 근거 행 2~3개로 정리하고,
예상 결과에서 목표 플래너로 이어지는 행동을 명확히 한다.
목표 플래너에서도 점수·단위·조건부 상태가 먼저 보이는지 함께 확인한다.

변경 전후 리뷰에서 다음을 확인한다.

- 입력을 줄였는가, 아니면 설정만 더 만들었는가?
- 3초 안에 현재 상태·예상 결과·다음 행동을 찾을 수 있는가?
- 실제 기록과 가정, 모르는 정보가 구분되는가?
- 계산 가능한 범위를 넘어 목표 달성을 약속하지 않는가?
- 새 기능이 기본 화면의 문장·조작 수를 늘리지 않는가?
- 모바일·키보드 조작, 저장 실패, 기존 데이터 복원이 유지되는가?
- 승인받은 파일 범위와 기존 계산 엔진 계약을 지켰는가?

이 문서는 제품 설계 기준이다. 새로운 모델의 정확성 입증이나 UI 구현 완료 보고를 대신하지 않는다.
