# 학식 메뉴 ID·별칭 정책 v1

적용: PHASE 3, 2026-11-13 KST. 구현은 `lib/dex/meal/identity.ts`, `aliases.ts`, `catalog.ts`다. 기존 설계 문서를 덮어쓰거나 개인 도감을 자동 이전하지 않는다.

## 네 가지 식별 범위

| 모델 | 의미 | 식별 정책 |
|---|---|---|
| Dish | 지속적인 대표 음식 또는 명확한 세트 | `dish-v1-` + SHA-256(identityKey), 날짜·식당·끼니·순번 제외 |
| MealOffering | 날짜·식당·끼니별 제공 식단 | source/date/cafeteria/mealTime/원문 이름/구성/가격/열량 튜플의 SHA-256 |
| CollectionEntry | 내 도감 카드 | 공통 저장소 UUID. owner+dex+dish가 같으면 재사용 |
| Experience | 실제 식사 1회 | 공통 저장소 UUID. 새 의도는 새 requestId, 같은 요청은 재전송 |

기존 MealItem.id는 `legacyMealItemId`로 보존하고 경험 context에 남긴다. 날짜별 ID나 `-2/-3` 코너 순번을 dishId로 쓰지 않는다. Offering의 sourceRecordKey와 ID에도 코너 순번을 넣지 않으므로 원본 배열/코너 순서 변경으로 다른 음식을 가리키지 않는다. 같은 내용의 중복 Offering은 조회 어댑터에서만 합친다. 공통/개인 저장소나 원본 JSON을 수정하지 않는다.

## 안전한 정규화

1. 유니코드 NFKC, 앞뒤 공백, 반복 공백, 소문자 key, key 안 공백 제거.
2. 알려진 HTML 표기 `&amp;`, `&#38;`, `&nbsp;` 해석.
3. 정확히 `[천원의 아침밥]` 행사 접두어만 제외.
4. 한국어 이름 뒤에 붙은 **영문 번역 괄호**만 제외. 한글 괄호 `(매운맛)` 등은 유지.
5. `돈까스 → 돈가스`, `치즈돈까스 → 치즈돈가스` 등 검토된 **전체 이름** 별칭만 적용.
6. 현재 저장본의 괄호 없는 한영 병기는 명시적 전체 이름 표에서 처리한다. 임의 번역·문장 추측·부분 문자열 치환은 하지 않는다.

`매운 제육볶음/간장 제육볶음`, `돈가스/치즈돈가스`, `비빔밥/돌솥비빔밥`, 단품/세트는 다른 ID다. 구성에 `*`, `&`, `/`가 있어도 원본 대표 이름이 명확하면 전체 세트를 한 메뉴로 다룬다. 반찬은 당시 경험 스냅샷에 남기고 대표 메뉴로 승격하지 않는다.
대표 이름 없음·메뉴 미정·휴무·일반 안내·충돌 별칭은 unresolved이며 수집 버튼을 비활성화한다. 영문 표현이나 수량 제한 등 판단하기 어려운 부분은 무리하게 지우지 않는다. 이 때문에 같은 음식의 일부 복잡한 표기는 자동 병합되지 않을 수 있다. 잘못 합치는 것보다 명시적 별칭 검토를 우선한다.

## 별칭과 개인 기록 보호

- MENU_ALIASES는 공용 코드 규칙이며 개인 기록이 아니다. 각 rawName은 canonicalName과 **고정 identityKey**에 연결된다. 같은 정규화 이름이 여러 identityKey를 가리키면 자동 판정하지 않는다.
- 한 번 사용한 v1 정규화 의미와 identityKey를 나중에 다른 음식으로 재배정하지 않는다. 향후 정규화 개선은 새 버전으로 검토한다.
- 새 별칭 추가 시 기존 fallback key로 이미 수집한 카드가 있을 수 있다. 이전 대상 ID를 확인하고 기존 ID로 연결하거나 명시적인 병합/분리 이전 계획을 먼저 작성한다. 무조건 새 canonicalName 해시로 재계산해 배포하지 않는다.
- 현재 조회는 기존 카드의 dishId·이름·경험·사진을 자동 수정하지 않는다. 별칭 변경으로 기존 기록이 사라지지는 않지만, 무계획한 재매핑은 미래 중복 카드를 만들 수 있어 자동 변경을 금지한다.
- 개인 카드 ID는 메뉴명에서 다시 계산하지 않는다. 이미 저장된 경험은 원문 이름/반찬/제공일/식당/끼니/사진/원본 ID/source의 스냅샷으로 남는다.
- 사진 경로는 기존 로컬 경로/원본 URL을 그대로 참조한다. 사진 바이너리를 별도 복제하지 않는다. 향후 명시적 크롤링이 같은 날짜·코너 파일을 덮어쓰는 문제는 내용 기반 자산 버전 정책으로 별도 해결할 항목이다.

## 출처와 시간

기존 `/api/meals/status` GET의 저장된 CrawlResult를 사용한다. 공식 학교 origin이고 실제 수집 성공 또는 cache 폴백인 결과만 수집 가능한 출처로 간주한다. seed/mock/미확인 출처는 실제 식사 등록을 막는다. `live` provenance 값은 저장 당시 수집 모드이며 현재 실시간 조회를 뜻하지 않는다.
마지막 성공 수집·실패 시도는 PHASE 1 상태 유틸을 따른다. cache의 fetchedAt을 성공 시각으로 바꾸지 않는다. 오래된 데이터는 오래됨과 저장 날짜를 표시하며 오늘 데이터로 채우지 않는다. Offering Versioned 필드는 가능한 경우 원본 fetchedAt을 사용하고, 없는 경우 epoch 기술 표식을 사용한다. 이 표식은 수집 성공 시각으로 표시하지 않으며 provenance의 null을 보존한다. Dish/Alias의 버전 시각은 규칙 발행일이며 식단 수집 시각이 아니다.
오늘/미래 식사 판단은 `lib/datetime.ts`의 KST 기준이다. 미래 제공일은 볼 수 있어도 먹은 기록으로 등록하지 않는다.

## 평가 대표값

경험 정렬은 먹은 날짜 내림차순 → 기록 생성 시각 내림차순 → ID 순이다. 수정 시각만 바뀐 오래된 식사가 새 식사보다 앞서지 않는다.
대표 별점은 정렬된 경험 중 **rating이 null이 아닌 첫 경험**이다. 최근 경험이 미평가면 이전 평가를 유지하고, 모두 미평가면 `평가 없음`이다. 최근 한줄평도 비어 있지 않은 첫 메모를 사용한다. 평균이나 공용 후기 평점을 합치지 않는다.
개별 경험 삭제는 다른 경험·카드를 유지한다. 카드 삭제는 연결된 모든 경험을 함께 삭제한다. 마지막 경험만 삭제하면 0회 카드가 남는 PHASE 2 정책을 유지한다.
