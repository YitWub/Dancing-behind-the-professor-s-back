# PHASE 4.2 게임 시스템 인수 메모

## 현재 동작

- 학식 개인 기록만 사용한다. 첫 발견/오늘 처음 등록한 새 메뉴/같은 메뉴 서로 다른 식사일 5일·10일/식당 3곳의 칭호와 기본 업적 6개를 구현했다. 메뉴 종류는 dishId별로 집계하므로 여러 개인 학식도감에 같은 메뉴가 있어도 중복 증가하지 않는다.
- 반복 방문 조건은 Experience.experiencedOn 기준의 서로 다른 날짜 수다. 같은 날짜 여러 기록은 경험 횟수에는 포함되지만 방문일 업적에는 1일이다. ‘오늘의 첫 발견’은 실제 식사일이 아니라 저장 결과 committedAt의 KST 등록일이며 설명에 구분해 둔다.
- 업적은 문서에서 계산한다. 경험 수정·삭제·카드 삭제·가져오기가 진행률과 현재 달성 상태에 바로 반영된다. 마지막 경험을 지워도 카드가 남는 기존 정책상 메뉴 종류 업적은 카드 삭제 전까지 유지된다. 최초 달성 시각은 수정/삭제 이력으로 복원할 수 없어 기록·표시하지 않는다.
- 알림 후보는 저장 성공·비재전송 결과에서 해당 경험을 제외한 직전 상태와 비교한다. 화면 열기·가져오기·수정 자체는 획득 팝업을 띄우지 않는다. 새 업적과 칭호는 기존 발견 모달/재방문 토스트에 합친다. 빠른 평가와 닫기·키보드·reduced-motion을 유지한다.
- `bokak.dex.game-notices.v1:<ownerId>` localStorage에는 확인한 이벤트/알림 ID만 보관한다. 이름·한줄평·진행률은 저장하지 않는다. 삭제 후 다시 조건을 충족해도 이미 본 알림은 재표시하지 않는다. 이 확인 기록은 도감 export에 포함되지 않는다. 다른 브라우저는 별도 확인 기록을 갖지만 기존 업적을 로딩만으로 다시 알리지는 않는다. 확인 기록 저장이 막히면 반복 가능한 알림을 생략하고 수집·업적 화면은 그대로 제공한다. 이 ledger는 여러 프로세스 간 트랜잭션 저장소가 아니며 수집의 중복 방지는 기존 requestId 엔진이 담당한다.
- 개인 대표 메뉴는 가장 많은 실제 경험, 가장 높은 대표 별점(최근 평가 있는 경험), 최초 등록, 최근 30일의 경험으로 계산한다. 미평가를 좋은 평가로 만들지 않으며 동률은 공동 표시한다. 단골/소울푸드는 반복 방문 칭호이고 메뉴의 제공 희귀도나 만족도 등급이 아니다.

## 희귀도와 관측 계약

현재 실제 메뉴는 모두 UNKNOWN이다. 관측 분모와 승인된 등급 경계가 없다. 현재 공용 저장본은 49개 식단, 제공일 5개(미래 날짜 포함)이며 마지막 확인 날짜 목록만 있고 날짜×식당×끼니의 정상 운영/완전 관측 여부는 없다. 수집 실패나 단순 빈 목록을 미등장/휴무로 바꿔 통계를 만들지 않았다.

`lib/dex/meal/rarity.ts`의 계약:

- MealObservation: 제공일·식당·끼니·출처·관측 시각·state(complete/partial/failed/closed/unknown)·identity 해석 완료 여부·dishIds.
- ObservationScope: 비교할 식당·끼니·시작일·종료일을 명시한다. ObservationRepository.list는 향후 영구 저장 어댑터용 포트이며 현재 운영 저장소 구현은 없다.
- 동일 단위의 최신 정상/명시적 휴무 기록을 선택한다. 같은 단위/메뉴 중복은 1회다. 실패·부분·미해결·빈 불명 상태·미래·범위 밖은 분모에서 제외한다. 후속 실패를 추가 미등장으로 세지 않는다. 같은 시각에 상충하는 기록은 불완전으로 취급한다. 주말 자체를 일괄 제외하지 않고 실제 운영 관측 여부를 따른다.
- 승인된 RarityPolicy와 충분한 단위·날짜·실제 출현이 모두 있어야 확정 등급을 반환한다. 운영 기본 정책은 **없다**. 경계·최소 표본을 이번에 임의 확정하지 않았다. 정책을 제공하지 않으면 관측이 많아도 UNKNOWN이다.
- 테스트 fixture의 4등급과 임계값은 테스트에서만 사용하며 실제 메뉴와 연결하지 않는다. UNKNOWN이 섞이거나 기준이 준비되지 않으면 희귀 업적 2개는 진행률 없이 ‘집계 준비 중’이다.
- 미수집은 ???, 수집 후 UNKNOWN은 ‘희귀도 조사 중’. 실제 메뉴명·가격·구성은 숨기지 않는다. UI 공개 연출은 보안 비밀이 아니다. RarityBadge와 공통 프레임은 opt-in이며 인연도감에 등급을 자동 부여하지 않는다.

장기 기록은 기존 영구 볼륨의 스냅샷 게시 경계를 활용할 수 있다. 다만 크롤러가 각 단위의 완전성·운영 여부·별칭 해석 상태를 명시적으로 산출하고 관측을 불변/버전 기록으로 함께 게시하는 후속 작업이 필요하다. 기존 checkedDates를 complete 관측으로 자동 이전하지 않는다. 이번에는 크롤러·동기화·식단 JSON·사진·개인 DB 스키마를 변경하지 않았다.

## 공통/담당 경계와 보류 범위

- A 공통: `lib/dex/game/types.ts`, `notices.ts`의 GameNotice·Achievement 표현 계약과 알림 확인. 공통 저장 엔진 공개 API는 그대로다.
- B 학식: `lib/dex/meal/game.ts`, `rarity.ts`, `components/dex/meal/MealGamePanel.tsx` 및 학식 연결. 관측·애정 판정을 공통 인연 기능으로 옮기지 않는다.
- D 공통 UI: `RarityBadge.tsx`, `GameNoticeList.tsx`, 기존 카드·발견 컴포넌트의 선택 props와 도감 전용 CSS. 인연·자유도감은 GameNotice만 재사용할 수 있다. 기존 CONTRACT.md를 변경하거나 새 소유권을 확정하지 않았다.
- 관심 목록은 후속이다. 별도 `MealInterest { ownerId, dexId, dishId, displayNameSnapshot, createdAt, updatedAt }`로 저장하고 CollectionEntry/Experience를 만들지 않는 포트를 권장한다. export/import 및 보존 계약과 함께 DB 버전 이전을 검토한 뒤 구현한다. 작동하지 않는 관심 버튼을 추가하지 않았다.
- 수집 번호도 보류했다. 현재 목록 index는 삭제/가져오기/동일 시각에서 바뀌므로 번호로 표시하지 않는다. 후속 구현은 최초 할당 ordinal을 불변 보존하고 삭제 번호를 재사용하지 않으며 export/import 충돌 정책까지 포함해야 한다. 학교 공식 메뉴 번호를 임의로 만들지 않는다.
- 장기간 미등장 후 복귀 칭호, 확정 희귀도 정책, 서버 계정·리더보드·알림 서비스는 비활성이다.

검증은 관련 개인 저장·게임·관측 fixture·실제 UI 계약 테스트 및 수정 파일 린트/타입, 격리 Chrome의 변경 흐름으로 한정했다. 실제 개인 브라우저 기록을 테스트에 사용하지 않았다.
