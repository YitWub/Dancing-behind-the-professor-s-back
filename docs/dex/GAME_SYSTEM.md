# PHASE 4.2 게임 시스템 인수 메모

## 현재 동작

- 학식 개인 기록만 사용한다. 첫 발견/오늘 처음 등록한 새 메뉴/같은 메뉴 서로 다른 식사일 5일·10일/식당 3곳의 칭호와 기본 업적 6개를 구현했다. 메뉴 종류는 dishId별로 집계하므로 여러 개인 학식도감에 같은 메뉴가 있어도 중복 증가하지 않는다.
- 반복 방문 조건은 Experience.experiencedOn 기준의 서로 다른 날짜 수다. 같은 날짜 여러 기록은 경험 횟수에는 포함되지만 방문일 업적에는 1일이다. ‘오늘의 첫 발견’은 실제 식사일이 아니라 저장 결과 committedAt의 KST 등록일이며 설명에 구분해 둔다.
- 업적은 문서에서 계산한다. 경험 수정·삭제·카드 삭제·가져오기가 진행률과 현재 달성 상태에 바로 반영된다. 마지막 경험을 지워도 카드가 남는 기존 정책상 메뉴 종류 업적은 카드 삭제 전까지 유지된다. 최초 달성 시각은 수정/삭제 이력으로 복원할 수 없어 기록·표시하지 않는다.
- 알림 후보는 저장 성공·비재전송 결과에서 해당 경험을 제외한 직전 상태와 비교한다. 화면 열기·가져오기·수정 자체는 획득 팝업을 띄우지 않는다. 새 업적과 칭호는 기존 발견 모달/재방문 토스트에 합친다. 빠른 평가와 닫기·키보드·reduced-motion을 유지한다.
- `bokak.dex.game-notices.v1:<ownerId>` localStorage에는 확인한 이벤트/알림 ID만 보관한다. 이름·한줄평·진행률은 저장하지 않는다. 삭제 후 다시 조건을 충족해도 이미 본 알림은 재표시하지 않는다. 이 확인 기록은 도감 export에 포함되지 않는다. 다른 브라우저는 별도 확인 기록을 갖지만 기존 업적을 로딩만으로 다시 알리지는 않는다. 확인 기록 저장이 막히면 반복 가능한 알림을 생략하고 수집·업적 화면은 그대로 제공한다. 이 ledger는 여러 프로세스 간 트랜잭션 저장소가 아니며 수집의 중복 방지는 기존 requestId 엔진이 담당한다.
- 개인 대표 메뉴는 가장 많은 실제 경험, 가장 높은 대표 별점(최근 평가 있는 경험), 최초 등록, 최근 30일의 경험으로 계산한다. 미평가를 좋은 평가로 만들지 않으며 동률은 공동 표시한다. 단골/소울푸드는 반복 방문 칭호이고 메뉴의 제공 희귀도나 만족도 등급이 아니다.

## 희귀도와 관측 계약

현재 실제 메뉴는 모두 UNKNOWN이다. 관측 분모와 승인된 등급 경계가 없다. 현재 공용 저장본은 49개 식단, 제공일 5개(미래 날짜 포함)이며 마지막 확인 날짜 목록만 있고 날짜×식당×끼니의 정상 운영/완전 관측 여부는 없다. 수집 실패나 단순 빈 목록을 미등장/휴무로 바꿔 통계를 만들지 않았다.

`lib/dex/meal/rarity.ts`의 계약:

- MealObservation: 제공일·식당·끼니·출처·관측 시각·state(complete/partial/failed/closed/unknown)·identity 해석 완료 여부·dishIds.
- ObservationScope: 비교할 식당·끼니·시작일·종료일을 명시한다. ObservationRepository.list는 향후 영구 저장 어댑터용 포트이며 현재 운영 저장소 구현은 없다.
- 동일 단위의 최신 정상/명시적 휴무 기록을 선택한다. 같은 단위/메뉴 중복은 1회다. 실패·부분·미해결·빈 불명 상태·미래·범위 밖은 분모에서 제외한다. 후속 실패를 추가 미등장으로 세지 않는다. 같은 시각에 상충하는 기록은 불완전으로 취급한다. 주말 자체를 일괄 제외하지 않고 실제 운영 관측 여부를 따른다.
- 승인된 RarityPolicy와 충분한 단위·날짜·실제 출현이 모두 있어야 확정 등급을 반환한다. 운영 기본 정책은 **없다**. 경계·최소 표본을 이번에 임의 확정하지 않았다. 정책을 제공하지 않으면 관측이 많아도 UNKNOWN이다.
- 테스트 fixture의 4등급과 임계값은 테스트에서만 사용하며 실제 메뉴와 연결하지 않는다. UNKNOWN이 섞이거나 기준이 준비되지 않으면 희귀 업적 2개는 진행률 없이 ‘집계 준비 중’이다.
- 미수집은 ???, 수집 후 UNKNOWN은 ‘희귀도 조사 중’. 실제 메뉴명·가격·구성은 숨기지 않는다. UI 공개 연출은 보안 비밀이 아니다. RarityBadge와 공통 프레임은 opt-in이며 인연도감에 등급을 자동 부여하지 않는다.
- 장기 기록은 기존 영구 볼륨의 스냅샷 게시 경계를 활용할 수 있다. 다만 크롤러가 각 단위의 완전성·운영 여부·별칭 해석 상태를 명시적으로 산출하고 관측을 불변/버전 기록으로 함께 게시하는 후속 작업이 필요하다. 기존 checkedDates를 complete 관측으로 자동 이전하지 않는다. 이번에는 크롤러·동기화·식단 JSON·사진·개인 DB 스키마를 변경하지 않았다.

## 획득 등급과 EXP

### 현재 구현 상태 (`lib/dex/game/exp.ts`)

랜덤 해시 등급은 폐기했다. 등급은 아래 도메인 기준에 따라 현재 기록에서 파생 계산하며 저장하지 않는다(DB 스키마·백업 형식 변경 없음).

- 내 경험치 = 소유한 학식·인연·강의 항목 등급 EXP의 합(`totalExp`). 기록이 보강되면 승급하고, 삭제하면 다시 계산되어 차감된다. 자유도감은 제외한다.
- 학식(`mealGrade`): 아래 1번 기준 전체 구현. 운영 중인 출현 희귀도 정책이 아직 없으므로 지금은 별점 반복 기준으로만 승급한다.
- 인연(`personGrade`): 아래 2번 기준 전체 구현. 메모·특징·추억은 공백 제외 10자 이상만 유효하며, 보드 연결은 인물↔인물 실(v1~3 edges, v4 person connections)만 센다. 아바타는 기본값(`classic`) 외 선택 또는 대표 이미지가 있으면 인정한다.
- 강의(`courseGrade`): 3-C의 `/grade` 미연결 하위 호환 등급(최대 희귀)만 구현. 3-A 활동 EXP·성취 축·3-D 예측 봉인은 3-E 마이그레이션 후속이다.

### 도메인별 등급·EXP 설계 기준 (목표 정책 · 허점 보완안)

공통 5등급 경험치는 **일반 10 / 고급 20 / 희귀 50 / 영웅 100 / 전설 300 EXP**로 통일한다. 대상은 `meal`·`person`·`course`이며 `custom`(자유도감)은 제외한다.

- **파생 계산 원칙 (삭제·재등록 파밍 차단)**: EXP는 별도 누적 카운터에 더하기만 하지 않고, 현재 보유한 유효 기록에서 결정적으로 파생 계산한다. 항목이나 기록을 삭제하면 해당 EXP도 즉시 차감된다. (단, 강의 예측 봉인 스냅샷은 사후 조작 방지를 위해 과목 엔트리에 불변 기록한다.)
- **로컬 앱 신뢰 한계**: 서버 인증·학교 포털 연동·공개 리더보드가 없는 로컬 브라우저 앱이므로, 일반 UI 흐름에서의 입력 피로·꼼수·역인센티브·개인정보 과입력 유도를 막는 데 초점을 둔다.

#### 1. 학식도감 (`meal`) — 보기 드문 메뉴 또는 맛있는 메뉴, 3등급

학식은 **일반 / 희귀 / 전설** 3등급만 쓴다(고급·영웅 없음). 업적의 "희귀 메뉴 수집가"·"전설의 미식가"와 같은 이름을 쓴다.

- **적립 단위**: 메뉴(`dishId`)당 1회. 여러 학식도감에 같은 메뉴가 있어도 한 번만 센다.
- **등급 기준**: 아래 두 기준 중 **높은 등급**을 쓴다.
  - **보기 드문 메뉴 (출현 희귀도)**: 승인된 `RarityPolicy`로 확정된(`confirmed` + `policyVersion`) 메뉴 희귀도가 `RARE`면 **희귀**, `LEGENDARY`면 **전설**. `COMMON`·`UNCOMMON`·`UNKNOWN`은 **일반**이다. 별칭 해석이 끝난 관측만 집계하는 기존 `rarity.ts` 계약을 그대로 따른다.
  - **맛있는 메뉴 (내 별점 반복)**: 서로 다른 날 별점 **4점 이상 2일** 이상이면 **희귀**, 서로 다른 날 **5점 3일** 이상이면 **전설**. 같은 날 여러 번 평가해도 1일로 센다.
- **EXP**: 일반 10 / 희귀 50 / 전설 300.
- **허점 보완 규칙**:
  - 별점 한 번으로는 승급하지 않는다. 처음 등록한 메뉴는 항상 일반에서 시작한다.
  - 관측 미확정(`UNKNOWN`) 기간에는 출현 희귀도가 승급에 기여하지 않는다. 별점 기준만 적용된다.
  - 평가·식사 기록을 삭제하면 다시 계산되어 등급과 EXP가 내려갈 수 있다.
- **화면 표시**: 학식 카드·카드 앨범·상세·발견 연출은 랜덤 카드 에디션(NORMAL/SPECIAL/RARE/GOLDEN) 대신 이 등급만 보여 준다. 에디션 필터·정렬·확률 안내는 제거했다. 저장된 카드 에디션 데이터와 개발자 도구(`/dex/dev/editions`, 컬렉션 실험실)는 그대로 둔다.

#### 2. 인연도감 (`people`) — 비민감 기록 깊이 & 추억 누적 기준

- **핵심 원칙**: 사람의 가치나 친밀도를 서열화하지 않는다. 기존 원칙(`별점이나 사람의 가치 등급은 제공하지 않아요`, 실명·사진 필수 금지)을 유지하며, 나이·성별·실제 프로필 사진 같은 **민감 개인정보 입력을 등급 상승 조건으로 강제하지 않는다.**
- **등급 기준** (메모·특징 유효 텍스트는 공백 제외 최소 10자 이상으로 더미 1글자 입력 차단):
  - **일반 (10 EXP)**: 표시 이름 등록 완료 (기본 등록)
  - **고급 (20 EXP)**: 이름 + 비민감 선택 정보 2개 이상(`relationship`, `department`, `admissionYear`, `mbti`, `energyType`, `trait` 중 선택) 또는 아바타·대표 이미지 설정
  - **희귀 (50 EXP)**: 고급 조건 + 첫 만남 메모(`first-met.note`, 10자 이상) 또는 추가 추억(`memory`) 1건 이상 기록
  - **영웅 (100 EXP)**: 희귀 조건 + **서로 다른 날짜의 추억(`memory`) 3일 이상** 누적 (또는 추억 2일 이상 + 보드 인연 연결 1건 이상)
  - **전설 (300 EXP)**: 희귀 조건 + **서로 다른 날짜의 추억(`memory`) 5일 이상** 누적 + 보드 인연 연결 1건 이상
- **허점 보완 규칙**:
  - 단발성 폼 채우기만으로 10초 만에 전설 카드를 양산하는 어뷰징을 막기 위해 `영웅`/`전설`은 **서로 다른 날짜의 추억 기록 누적**을 필수로 둔다.
  - 정보·추억이 보강되면 상위 등급으로 자동 승급(차액 EXP 반영)되며, 삭제 시 재계산된다.

#### 3. 강의도감 (`course`) — 활동 누적 EXP + 2축 카드 등급 + 예측 봉인 보너스

기존 `/grade` 학점 관리(`lib/grade/UX_GUIDELINES.md`, `lib/grade/tier.ts`, `lib/grade/attendance-estimate.ts`)의 설계 원칙(예외 중심 입력, 거짓 정밀도 금지, 예정/대기 0점 처리 금지)과 충돌하지 않도록 활동 EXP·예상 학점·카드 등급·예측 보너스의 역할을 분리해 연결한다.

- **A. 활동 누적 EXP (수강 노력 보상 · 과목당 상한 적용)**
  - **출석**: 정상 출석 인정 1회당 **+3 EXP** (과목당 `totalSessions` 상한, 기본 15회 → **최대 45 EXP**). 매 수업 수동 클릭을 강제하지 않고 `/grade` 출석 관리(결석·지각 예외 기록 기반 정상 출석 산출) 또는 주차별 일괄 확인과 연동하며, 결석(`absent`)·총 수업 횟수 초과 입력은 미지급한다.
  - **과제**: 과제 1건 제출·채점 기록(`awaiting_grade` 또는 `graded`)당 **+8 EXP** (과목당 5건 상한 → **최대 40 EXP**). 미제출 0점 확정(`zero_confirmed`)은 제외한다.
  - **시험**: 중간·기말 등 시험 1건 응시·채점 기록(`awaiting_grade` 또는 `graded`)당 **+15 EXP** (과목당 3건 상한 → **최대 45 EXP**). 미응시 0점 확정(`zero_confirmed`)은 제외한다.
  - → 과목당 활동 누적 EXP 상한 **130 EXP**로 제한해 타 도감과의 EXP 밸런스 붕괴 및 무한 클릭 파밍을 차단한다.
- **B. 예상 학점 연동 원칙**
  - 출석(성적 반영 비율 > 0%인 과목)·과제·시험 기록이 반영되면 예상 학점과 성적 HP(확보 점수)는 `/grade` 계산 엔진 규칙대로 실제 결과에 따라 갱신한다.
  - **무조건 상승 금지**: 시험·과제 저득점 시 예상 학점은 하락할 수 있으며, 반 평균·표준편차가 없는 Tier 0/1 과목은 예상 등급을 지어내지 않고 확보 점수·성적 HP만 갱신한다. 출석은 만점 출발·결석 감점 모델이므로 출석 유지가 곧 확보 점수 유지·방어에 기여한다.
- **C. 강의 카드 등급 (`일반`~`전설`, 10~300 EXP) — 노력(진행·기록) + 성취 2축 합산 (최대 8점)**
  - 예상 학점(A+~F) 단독으로 등급을 매기면 어려운 전공을 완주한 학생보다 쉬운 교양만 유리해지고 시험을 망친 학생에게 이중 페널티가 생기므로 2축으로 산정한다.
  - **진행·기록 축 (최대 5점)**:
    - 출석 유지율 80% 이상(또는 출석 미반영 과목은 수강 중/완료 유지): **+1점**
    - 출석 반영 과목에서 유지율 90% 이상(출석 비중 0% 과목은 평가 기록 완료율 100%로 대체 인정해 과목 유형 간 불공정 해소): **+1점**
    - 예정된 과제·시험 기록 완료율 50% 이상: **+1점**, 100% 완료(`completed`): **+1점** (누적 +2점)
    - 개인 강의 리뷰(`CourseReview` 한줄평·난이도·과제량 등) 작성: **+1점**
  - **성취 축 (최대 3점 · 최고 해당 구간 1개만 적용, `/grade` 연동 또는 확정 성적 입력 시)**:
    - 예상·확정 성적이 목표 학점 도달 또는 B0 이상(확보 점수 75점 이상): **+1점**
    - 예상·확정 성적이 A0 이상(확보 점수 85점 이상): **+2점**
    - 확정 성적 A+(또는 절대평가 만점/목표 초과 달성 + 완주): **+3점**
  - **등급 구간**: **일반** 0~1점(10 EXP) / **고급** 2~3점(20 EXP) / **희귀** 4~5점(50 EXP) / **영웅** 6~7점(100 EXP) / **전설** 8점(300 EXP).
  - `/grade`를 연결하지 않은 단독 강의도감 사용자는 `수강 예정`(일반) · `수강 중` 또는 리뷰 없는 `수강 완료`(고급) · `수강 완료 + 리뷰 작성`(희귀)까지 획득할 수 있도록 하위 호환을 유지한다.
- **D. 예상 성적 vs 실제 성적 보너스 (예측 봉인 · 역인센티브 차단)**
  - **예측 봉인(Snapshot Lock-in) 필수**: 종강 후 실제 성적을 보고 예상 성적을 끼워 맞추는 사후 조작을 막기 위해, **실제 성적 확정 전 사용자가 '예측 봉인'을 눌러 불변 스냅샷(예측 단일 등급 또는 예측 구간, 봉인 시각, 봉인 시점 반영 평가 비율 50% 이상)을 잠근 과목**만 보너스 자격을 갖는다. 봉인 후 예측 수정은 불가하며 과목당 1회만 판정한다.
  - **보너스 지급 기준**:
    - **정확 적중** (봉인된 단일 예상 등급 == 실제 확정 성적): **+50 EXP**
    - **구간 적중** (상대평가 구간 예측 예: `A0~B+` 안에 실제 성적 포함): **+30 EXP**
    - **기대 이상 돌파** (실제 확정 성적 > 봉인된 예상 등급 상한): **+50 EXP** — 일부러 성적을 낮춰 예상에 맞추는 역인센티브를 원천 차단하기 위해 적중과 동등 보상한다.
- **E. 저장소·연동 경계 (후속 구현 전제)**
  - 현재 강의도감(`IndexedDB` `CourseSubject`)과 학점 관리(`localStorage` `erica.grade.courses.v2` `ManagedCourse`)는 저장소가 분리되어 있다. 이중 입력을 피하려면 `CourseSubject`에 선택적 연결 키(`linkedGradeCourseId`)와 예측 봉인 스냅샷·실제 확정 성적 필드를 추가하는 스키마·백업 마이그레이션이 필요하다.

## 공통/담당 경계와 보류 범위

- A 공통: `lib/dex/game/types.ts`, `notices.ts`의 GameNotice·Achievement 표현 계약과 알림 확인. 공통 저장 엔진 공개 API는 그대로다.
- B 학식: `lib/dex/meal/game.ts`, `rarity.ts`, `components/dex/meal/MealGamePanel.tsx` 및 학식 연결. 관측·애정 판정을 공통 인연 기능으로 옮기지 않는다.
- D 공통 UI: `RarityBadge.tsx`, `GameNoticeList.tsx`, 기존 카드·발견 컴포넌트의 선택 props와 도감 전용 CSS. 인연·자유도감은 GameNotice만 재사용할 수 있다. 기존 CONTRACT.md를 변경하거나 새 소유권을 확정하지 않았다.
- 관심 목록은 후속이다. 별도 `MealInterest { ownerId, dexId, dishId, displayNameSnapshot, createdAt, updatedAt }`로 저장하고 CollectionEntry/Experience를 만들지 않는 포트를 권장한다. export/import 및 보존 계약과 함께 DB 버전 이전을 검토한 뒤 구현한다. 작동하지 않는 관심 버튼을 추가하지 않았다.
- 수집 번호도 보류했다. 현재 목록 index는 삭제/가져오기/동일 시각에서 바뀌므로 번호로 표시하지 않는다. 후속 구현은 최초 할당 ordinal을 불변 보존하고 삭제 번호를 재사용하지 않으며 export/import 충돌 정책까지 포함해야 한다. 학교 공식 메뉴 번호를 임의로 만들지 않는다.
- 장기간 미등장 후 복귀 칭호, 확정 희귀도 정책, 서버 계정·리더보드·알림 서비스는 비활성이다.

검증은 관련 개인 저장·게임·관측 fixture·실제 UI 계약 테스트 및 수정 파일 린트/타입, 격리 Chrome의 변경 흐름으로 한정했다. 실제 개인 브라우저 기록을 테스트에 사용하지 않았다.
