# 안전한 학식 자동 최신화 운영

현재 저장소에는 배포 공급자·운영 cron 설정이 없다. `.vercel`의 유무나 템플릿 로고를 실제 배포의 증거로 간주하지 않았다. 구현한 어댑터는 **상시 Node 서버 + 영구 파일 볼륨**용이다. 현재 개발 서버만 실행하면 자동 수집되지 않는다.

## 운영 설정

1. Next 서버와 별도 작업자에 **같은 `MEALS_STORAGE_DIR`** 절대 경로를 설정한다. 재배포·재시작 후에도 유지되는 볼륨이어야 한다. 서버 여러 대의 각기 다른 로컬 디스크를 같은 저장소처럼 사용하지 않는다.
2. `npm run meals:schedule`을 별도 서비스로 상시 실행한다. Node 24 사용. systemd/컨테이너 서비스/Windows 서비스 관리자에서 이 명령을 관리하고 재시작·로그 수집을 설정한다. 서비스 등록 자체는 이번 작업에서 실행하지 않았다.
3. 기본 시각은 `config/meal-sync.json`의 **07:00, 11:00 KST**. `MEALS_SYNC_TIMES=08:00,12:00`으로 덮어쓸 수 있다. 변경 후 작업자를 재시작한다. 최대 약 30초의 확인 지연이 있으며 정밀 실시간 작업이 아니다.
4. 작업자가 늦게 시작되면 같은 한국 날짜의 가장 최근 지난 슬롯 1개를 처리한다. 성공·실패한 슬롯은 중복 실행하지 않고 다음 슬롯까지 기다린다. 다른 수집의 잠금 때문에 실행하지 못한 경우에는 다시 확인한다.

```powershell
# 서버와 작업자 모두에 설정. 예시 경로가 실제 영구 볼륨인지 운영자가 확인해야 한다.
$env:MEALS_STORAGE_DIR='D:\BOKAK-runtime\meals'
npm run meals:schedule
```

`npm run meals:schedule -- --check`는 설정만 확인하며 수집하지 않는다. `--once`는 현재 도래한 슬롯 1개를 처리하고 종료한다. 정규 스케줄러가 이 once 명령을 실행하도록 설정할 수도 있다. 작업자·OS 스케줄러가 켜져 있지 않으면 자동으로 실행되지 않는다. 현재 로컬 개발 PC에 예약 작업을 설치하지 않았다.

기존 `npm run meals:sync`는 즉시 수집용으로 유지한다. `--date=YYYY-MM-DD`, 반복 가능한 `--extra-date=YYYY-MM-DD`, `--out=저장소외부/preview.json`을 지원한다. out은 미리보기이며 이미지 다운로드·운영 상태·스냅샷을 변경하지 않는다. 기존 종료코드 계약상 manual 명령은 수집 실패에도 exit 0이므로 **로그/결과의 ok와 마지막 시도 상태를 확인**한다. once 작업자는 실패 시 exit 1이다.

## 데이터 보호

- 기본 로컬 저장 위치는 `data/meal-sync/`이고 Git에서 제외된다. 운영에서는 프로젝트 밖 영구 볼륨을 권장한다.
- 기존 data/meals.json, meal-photo-db.json, public/meals 이미지는 첫 스냅샷의 입력으로만 사용하며 덮어쓰지 않는다.
- 새 수집은 공식 출처·날짜·메뉴·가격을 검사한다. 일부 상세 요청/HTML 구조가 실패하거나 기존 같은 날짜보다 항목이 줄어들면 게시를 보류한다. 확인된 새 날짜에 실제 메뉴가 없으면 오늘 메뉴를 만들지 않고 과거 식단을 유지한다.
- 날짜·식당·끼니·원문 메뉴명 기준으로 병합한다. 기존 항목 ID를 유지하고 서로 다른 메뉴의 코너 ID 충돌을 분리한다. 개인 dishId 규칙과 IndexedDB는 변경하지 않는다.
- 사진은 공식 uploads URL만 수집하고 응답 크기·MIME·시그니처를 검사한다. 내용 해시 파일명으로 저장하며 기존 파일을 덮어쓰거나 삭제하지 않는다. 정확히 같은 제공 식단·구성이면 기존 사진을 재사용한다. 다운로드가 실패하면 같은 식단의 기존 사진을 우선 보존한다.
- 식단과 사진 매핑을 변경 불가 generation JSON으로 임시 기록·검증한 뒤 `current.json`을 원자 교체한다. 독자는 이전 또는 새 전체 스냅샷을 읽으며 반쪽 매핑을 보지 않는다. 이전 generation은 지우지 않는다. 새 사진은 검증 후 추가만 하며 게시 중단 시 미참조 새 파일이 남을 수 있으나 기존 사진에는 영향이 없다.
- 실패 시 current와 마지막 정상 수집 시각은 그대로이고 `last-attempt.json`만 실패 상태로 갱신된다. GET은 이 상태와 실제 제공 날짜·오래됨을 읽을 뿐이다.
- `sync.lock`은 파일시스템의 배타적 생성으로 획득한다. 여러 작업자가 같은 영구 볼륨을 써야 한다. 비정상 종료 잠금은 시간을 이유로 자동 탈취하지 않는다. 운영자가 PID가 종료됐고 수집이 없음을 확인한 뒤 해당 잠금 파일만 해제한다. 공유 파일시스템은 배타 생성·원자 rename 보장을 별도 확인한다.
- 보존 정책상 이력·사진을 자동 삭제하지 않는다. 디스크 용량·외부 백업은 운영자가 관리한다.

## 서버리스 배포

Vercel/Lambda의 임시 파일시스템에 이 파일 어댑터를 그대로 쓰는 경로는 거부한다. Vercel 등에 배포한다면 객체 저장소(S3/Blob 등)의 불변 스냅샷·사진, DB의 조건부 포인터 갱신·실행 잠금, 해당 플랫폼 스케줄러를 연결해야 한다. 현재 연결된 계정·배포 대상이 없어 이를 실제 구성했다고 주장하지 않는다. 무인증 크롤링 실행 HTTP API는 추가하지 않았다. 사진 GET만 공개되며 수집·파일 쓰기·개인 데이터 접근은 하지 않는다.
