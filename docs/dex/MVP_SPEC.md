# BOKAK 2.0 — 나만의 대학도감 / 현재 기준

## 지금 참고할 기준 (2026-11-14)

- 공식 진입점은 `/` → `/dex`. 기존 홈페이지는 `/legacy`, 학점 `/grade`, 꿀강 `/honey`, 기존 학식 `/meal`로 보존한다. 개발은 BOKAK-dex-integration에서 실행한다.
- 구현됨: 도감 허브·공통 IndexedDB 엔진·내보내기/가져오기, 학식 조회·수집·재방문·Experience 평가/수정/삭제, 업적·특별 발견 칭호. 인연·자유도감은 현재 조회 골격이며 등록·편집 전체 기능이 완성된 상태는 아니다.
- 메뉴 출현 희귀도는 보류하며 실제 메뉴는 UNKNOWN. DishFamily·출현 이력·통계 계산과 `/dex/dev/rarity` 미리보기는 보존한다. 개발 미리보기는 프로덕션에서 404이며 개인 기록·업적에 연결하지 않는다.
- 다음 단계는 랜덤 카드 에디션과 카드 앨범. `Dish`=음식 종류, `CollectionEntry`=음식 발견 등록, `Experience`=실제 식사, `CardInstance`=경험에서 획득한 개별 카드, `CardEdition`=랜덤 에디션이다. 후자의 두 모델은 아직 미구현이다. 예시 NORMAL/RARE/GOLDEN은 확정된 타입·확률이 아니다.
- 같은 음식은 등록 1개에 경험을 누적하는 현재 동작을 유지한다. 후속 카드 앨범은 메뉴 도감과 분리한다. 랜덤 에디션은 음식의 제공 빈도·맛·가치 등급이 아니며 기존 `rarity.ts`를 전용하지 않는다.
- 주요 위치: `app/dex/`, `components/dex/meal/`, `components/dex/discovery/`, `lib/dex/core/`, `lib/dex/storage/`, `lib/dex/meal/`, `lib/dex/game/`. 출현 분석은 `lib/meal/history*.ts`, `family-analysis.ts`, `config/meals/analysis-mappings.v1.json`이다.
- 후속 CardInstance 저장은 공통 모델·수집 트랜잭션·requestId 영수증·저장소 마이그레이션·export/import를 함께 설계한다. 재전송 때 재추첨하지 않는 계약, 과거 경험의 카드 소급 발급 여부, 경험 삭제 시 카드 보존 정책은 구현 전에 결정한다. 이번 단계에서는 DB·dishId·업적 계산을 변경하지 않았다.
- 데이터 보존 우선. 일반 조회·개발 시작·빌드에서 크롤링하지 않는다. 기존 식단·사진·개인 기록·다른 워크트리는 수정하지 않는다. 아래 PHASE 0 초안은 당시 배경이며 현재 구현과 충돌하면 실제 코드와 이 현재 기준을 우선한다. 루트 CONTRACT.md의 소유권은 별도 협의 대상이다.

## 보존된 PHASE 0 MVP 초안

상태: PHASE 0 검토안, 2026-11-12 KST. 기능 구현 전 팀 합의 대상이다. 기존 루트 CONTRACT.md를 대체하지 않는다.

## 목적

**대학생활의 모든 발견을 수집하다.**

사용자가 대학생활 중 직접 경험한 음식, 사람, 장소, 활동을 자신의 도감에 수집하고 기록한다.
핵심 흐름은 발견 → 수집 → 신규 발견 연출 → 평가·메모 → 도감에서 다시 확인이다.
모든 도감은 개인 기록이다. 초기 MVP에는 로그인, 공개 피드, 타인 검색, 서버 계정·기기 동기화가 없다.
데이터는 현재 사이트 주소(origin)의 브라우저 프로필에 저장된다. 같은 프로필을 사용하는 사람은 접근할 수 있으므로 인증된 비공개 서비스로 표현하지 않는다.

## MVP 범위

| 도감 | 포함 | 제외 |
|---|---|---|
| 학식 | 오늘 메뉴·식당·끼니 조회, 실제 먹은 메뉴 선택, 첫 수집, 1~5 정수 별점·한줄평(선택), 재방문, 수집 목록·상세·경험 수정/삭제 | 공개 후기·식당 승부·추천 순위 |
| 인연 | 표시 이름/별명, 선택 입학 연도·학과·관계·메모, 조건 기반 발견 메시지, 목록·상세·수정·삭제 | 실명·전체 학번·연락처·사진 필수, 별점·가치 등급·공개 평가 |
| 자유 | 도감 이름·아이콘, 생성·수정·삭제, 항목 제목·메모·수집 날짜, 항목 CRUD·개인 목록 | 무제한 커스텀 필드 편집기·전체 대상 수 강제 |

기존 학점·HP·희망/현실/절망회로·GPA·OCR·꿀강은 MVP 밖이다. 코드·테스트·데이터·설계 문서와 기존 브랜치를 보존한다. PHASE 0에서는 기존 화면도 변경하지 않는다.

## 수집 정책 초안

1. 학식은 대표 메뉴(예: 제육볶음)를 수집 단위로 하고 반찬·가격·사진·식당·제공일은 경험 당시 스냅샷에 둔다. 세트는 우선 세트 한 항목이다.
2. 제육볶음 3회 식사는 카드 1개 + 경험 3개다. 다른 식당에서 같은 Dish를 먹어도 같은 개인 학식 카드에 쌓는다. 이 범위는 팀 최종 합의가 필요하다.
3. 항목 선택만으로 저장하지 않는다. 명시적 수집 요청을 제출한다. 별점·메모 없이도 수집 가능하며 이후 보완한다.
4. 같은 요청 재전송은 같은 requestId를 재사용한다. 별도 재방문은 새 requestId를 쓴다. 날짜만으로 중복 금지하지 않는다.
5. 저장 트랜잭션 완료 후에만 신규 연출한다. 실패하면 입력·requestId를 보존하고 재시도한다. mock 객체로 저장 성공을 대신하지 않는다.
6. 현재 세션의 신규 저장에만 연출한다. 재전송 응답·새로고침·목록 조회는 신규 연출하지 않는다. 모션 감소, 건너뛰기, 키보드·스크린리더 피드백을 지원한다.
7. 인연의 같은 이름은 중복 판정 기준이 아니다. 학번 차이는 분위기 있는 문구를 고르는 조건일 뿐 사람의 가치·희귀 등급이 아니다. 정보가 없으면 일반 메시지를 쓴다.
8. 기본 진행 표시는 수집 개수다. 명시적으로 닫힌 대상 목록이 정의된 도감만 선택적으로 완료율을 지원한다. 자유·인연·지속적으로 추가되는 학식에 임의 분모를 붙이지 않는다.
9. 학식 카드 대표 평가는 최근 평가가 있는 경험의 별점으로 제안한다. 평균·방문 횟수는 경험에서 계산하며 과거 평가를 덮어쓰지 않는다.
10. 기존 공용 MealReview에는 소유자를 증명할 정보가 없으므로 개인 경험으로 자동 이관하지 않는다.

## PHASE 0 이후 첫 완료 기준

사용 시나리오: 오늘 제공된 메뉴 하나를 선택 → 영속 메뉴 ID 확인 → 개인 도감 등록 → 신규 연출 → 동일 메뉴 재방문 → 새로고침 후 카드/이력 확인.

- 기존 식단을 읽는 과정에서 JSON·사진 변경이나 외부 크롤링이 발생하지 않는다.
- B의 read-only 어댑터가 원문과 legacy ID·출처를 유지한다. 메뉴 매핑이 불명확하면 사용 가능한 후보/확인 상태를 표시하고 임의 합치지 않는다.
- 첫 저장은 카드 1개·경험 1개·요청 영수증을 원자적으로 저장한다.
- 같은 requestId 재시도는 같은 entryId·experienceId를 반환하며 새 기록이나 신규 연출이 없다. 다른 payload로 같은 ID를 재사용하면 오류다.
- 새 requestId로 재방문하면 카드 1개·경험 2개다. 같은 날 두 번의 실제 식사도 가능하다.
- 성공은 IndexedDB transaction complete 이후 반환한다. 저장 실패·quota·취소 시 성공 UI를 표시하지 않는다.
- 같은 사이트 주소·브라우저 프로필에서 새로고침 후 데이터가 유지된다.
- 중복 요청·동시 탭·실패 복구·날짜 경계·모션 감소를 검증한다.
- 수집 목록/최소 상세에서 방문 횟수와 이력을 확인한다. 전체 UI 개편이나 인연·자유 기능 완성은 이 첫 작업 범위에 넣지 않는다.

## 사용자 기록 보존

개인 데이터 내보내기/가져오기는 MVP의 보존 기능이다. 내보낸 JSON은 인연·메모를 포함하는 민감한 파일일 수 있음을 안내한다. 기본 출력은 평문이며 암호화 보장을 하지 않는다. 로그·서버 업로드·Git·public에 개인 데이터를 쓰지 않는다.
사이트 데이터 삭제, 비공개 모드, 저장 용량 부족, origin/포트 변경은 기록 접근에 영향을 준다. 저장 영속성 요청은 최선의 보조 수단이며 백업을 대체하지 않는다.
기존 학점 localStorage는 별도 대상이다. 사용자가 기존 origin에서 erica.grade.courses.v1, erica.grade.courses.v2, erica.grade.quick.v1, erica.grade.editor-draft.v1.*를 직접 내보내 보관해야 한다. Git·파일 백업에 포함되지 않는다.

## 합의가 필요한 사항

- 메뉴 동일성: 식당 간 공유 범위, 변형/세트 분리, 불명확 매핑 확인 담당.
- 한줄평 제한(제안 200자), 인연 메모 제한(제안 500자), 도감·항목 이름 제한.
- 대표 별점 표시와 초기 아이콘 목록.
- 도감·카드 삭제 확인 UX, 경험 0건 카드 정책(초안은 빈 카드 보존, 명시적 카드 삭제).
- 내보내기 복원 전략(초안은 검증 후 전체 교체), 향후 암호화·병합 도입 여부.
- 새 CONTRACT의 승인 주체와 공유 파일 변경 예약 방식.
